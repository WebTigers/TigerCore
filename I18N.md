# Tiger — Internationalization (i18n / l10n)

How every user-facing string in Tiger is localized, and — the payoff — how a **new language is a drop-in**:
translate the key files, add the locale to config, done. No code scan, no view surgery. Read this before
touching a language file, a view string, or the translator. For the platform *why* read
[ARCHITECTURE.md](ARCHITECTURE.md) (§5 config cascade); for conventions read [AGENTS.md](AGENTS.md) (the i18n
section).

> **Status: the whole-app keying pass is done.** Every form error, `/api` response message, error page, view
> string, and user-facing library string is a **semantic key**. `en` is the source; `es` is fully translated;
> `pt` / `de` / `fr` / `hi` ship as **stubs** (keys present, English placeholders) to prove the drop-in path.

---

## 0. The one principle

**A user-facing string is never a literal — it is a semantic key resolved against the active locale.** The
literal English lives in `languages/en/*.php`; every other locale is the same keys with translated values. So
"add Portuguese" = fill `languages/pt/*.php`, never grep the codebase again.

---

## 1. Where strings live — the cascade

The translator (`Zend_Translate` AN_ARRAY) is built once in `Tiger_Application_Bootstrap::_initTranslate`,
per supported locale, in this order (**last wins**):

```
core/languages/<lang>/core.php              (package — the default namespace + kernel strings)
  → modules/<mod>/languages/<lang>/<mod>.php (each first-party + app module)
    → application/languages/<lang>/app.php    (the app's own global overrides)
      → the `translation` DB table (global scope)   — live overrides, no deploy
```

Each file returns a flat `[key => string]` map:

```php
<?php  // modules/cms/languages/es/cms.php
return [
    'cms.page.saved'   => 'Página guardada.',
    'cms.page.title'   => 'Título',
    'cms.page.deleted' => 'Página eliminada.',
];
```

**Supported locales** are `tiger.i18n.locales` in `configs/core.ini` (`en,es,pt,de,fr,hi`); the default is
`tiger.i18n.default` (`en`). The request language resolves URL `/xx/` prefix → cookie → `Accept-Language` →
default (`Tiger_Controller_Plugin_LocalePrefix`), and the header switcher writes the cookie + localStorage.

---

## 2. Keys — the naming contract

`<owner>.<area>.<type>.<name>`, **owner-prefixed** so two modules never collide:

- **owner** — `core.*` (framework / default namespace), `app.*` (the app), `<module>.*` (a module: `cms.*`,
  `blog.*`, `agent.*`).
- then a **semantic** tail describing intent, not the English words — `cms.page.saved`, not `cms.the_page_was_saved`.

Keys are **language-independent**: the key is the same in every locale; only the value changes. A key that
appears in `en` **must** appear in every other locale's file (stubs included) — that parity is what makes a
locale complete.

---

## 3. How each surface localizes

| Surface | How | Rule |
|---|---|---|
| **Form labels / errors** | `Tiger_Form::_t('key')` (declared in `elements()`) | keys only; the base returns the key verbatim if untranslated |
| **`/api` responses** | `_success($data,'key')` / `_error('key')` / `_formErrors($form)` | keys only — `Tiger_Model_MessageObject` translates in the caller's locale automatically |
| **Error pages (403/404/500)** | `core.error.*` keys in the error view | keys only |
| **Views (`.phtml`)** | **`$this->t('key')`** (the `Tiger_View_Helper_T` helper) | NEVER a bare English literal; NEVER `$this->_t()` (unregistered — throws) |
| **Library (`Tiger_*`)** | emit a **key** through the normal message/exception path; never a hardcoded user-facing sentence | a class that shows a string to a user uses a `core.*` key |

**Views — the one gotcha.** `$this->_t()` does **not** exist in a view (the plugin isn't registered — it
throws `Plugin '_t' not found`). Use **`$this->t('key')`** — the `Tiger_View_Helper_T` helper. It resolves
against the shared translator, returns the key if untranslated (visible + greppable, never blank), and
`vsprintf`s trailing args into `%s`/`%d` placeholders: `$this->t('cms.page.count', $n)`. Escape output as
usual: `<?= $this->escape($this->t('...')) ?>`.

---

## 4. Adding a new locale (the payoff — no scan)

1. For each `languages/en/<file>.php`, add a sibling `languages/<lang>/<file>.php` with the **same keys**,
   values translated. (Copy the `en` file, translate the values — the key set is the checklist.)
2. Add the locale to `tiger.i18n.locales` in `configs/core.ini` (or an app override).
3. That's it — the switcher lists it, `/xx/` URLs resolve, the DB-override tier still applies on top.

No controller, view, form, or service changes — because every string is already a key. The stub locales
(`pt`/`de`/`fr`/`hi`) are step 1 half-done: the files exist with English placeholders, so a translator only
overwrites values.

---

## 5. Stub locales

`pt` / `de` / `fr` / `hi` ship as **stubs**: every `en` key is present, values are the English text with a
`// STUB — translate the values` header. So the locale is **selectable and functional today** (falls back to
readable English) and **trivially completable** (overwrite values, no key hunting). This is the honest form of
"scaffolded" — no fake-translated strings, no missing keys.

---

## 6. Rules of thumb

- **Never** hardcode a user-facing string — a form label, a toast, a button, a heading, an error. Key it.
- **Key parity is the contract:** every `en` key exists in every locale file. A missing key in `es` shows
  English (fail-soft) but counts as incomplete.
- **Keys are semantic, not English:** `agent.error.unconfigured`, not `agent.the_agent_is_not_set_up`.
- **The value is the only thing that varies by locale.** Never branch on locale in code — resolve a key.
- **Escaping is still the view's job** (`$this->escape(...)`); the translator returns raw text.
- A **CMS content body** (a page a user authored) is data, not a UI string — it is not keyed (it lives per
  locale as its own `page` row; §CMS).
